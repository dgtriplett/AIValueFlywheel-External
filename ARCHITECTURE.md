# Architecture

A single Databricks App: FastAPI serving a React single-page app, backed by one of two
app-state stores, with Unity Catalog for discovery and Foundation Model endpoints
behind the agents. Deployed and upgraded by a Databricks Asset Bundle.

```
┌──────────────────────────── Databricks App ────────────────────────────┐
│  FastAPI (app.py)                                                       │
│   ├─ /api/*   REST (server/routes/)                                     │
│   ├─ /console dependency-free discovery console (frontend/console)      │
│   └─ /        React SPA (frontend/dist, built from frontend/src)        │
│  Identity: the app's service principal; users via forwarded headers     │
└──────┬───────────────────────────┬─────────────────────┬───────────────┘
       │ server/db.py              │ Statement Execution │ chat / ai_query
       ▼                           ▼ (bound warehouse)   ▼ (serving endpoints)
 ┌──────────────────────────┐ ┌─────────────────────┐ ┌──────────────────┐
 │ App state — ONE of:      │ │ Unity Catalog        │ │ Foundation Model │
 │  • Lakebase (asyncpg)    │ │  discovery inventory │ │  agents          │
 │  • Delta via warehouse   │ │  system tables       │ │                  │
 └──────────────────────────┘ └─────────────────────┘ └──────────────────┘
```

## Product surfaces

- **Operate** (`OperateView.tsx`): the business unit's roadmap and portfolio — pillar
  progress, priority, readiness, coverage, data status, value, what-if, reconciliation
  and discovery. Each use case's drawer adds the roadmap's own context (why it matters,
  KPI, value estimate and assumptions, first-version plan).
- **Roadmap import** (`RoadmapImportModal.tsx`, `server/routes/roadmap_import.py`):
  seeds and refreshes the portfolio from a roadmap. The upload is either the AI
  Transformation Roadmap (AITR) deck (`.html`), which `server/aitr_deck.py` reads into a
  package in memory, or a roadmap package (`.json`, [ROADMAP_PACKAGE.md](ROADMAP_PACKAGE.md)).
  `server/roadmap_package.py` validates it, suggests a catalog match for every use case
  and diffs it against the last version; a person confirms every row before anything
  is written. History lives in `roadmap_imports`; pillars in `account_pillars`; what the
  roadmap said about each use case in `account_roadmap_use_cases`.
- **Explore** (`ExploreView.tsx` over `RoadmapView.tsx` / `RoadmapBlastRadius.tsx`): the
  shipped catalog as a dependency map. Selecting a use case shows its blast radius
  (prerequisites, what it unlocks, shared data); the business unit's portfolio is
  highlighted and any use case can be added to it (`/api/explore/portfolio`).
- **Authoring** (`server/authoring.py`, `server/routes/authoring.py`,
  `AuthorUseCaseModal.tsx`): add a use case by hand; the agent proposes its mappings,
  a person reviews them, and a confirm token performs the write.
- **Admin** (`AdminView.tsx`): setup health, business units, backup, catalog editors,
  value assumptions, feature flags, admins.

## Multi-tenancy: business units

Each business unit is an `accounts` row. Per-unit state (portfolio membership,
data-asset status, imported roadmaps and pillars, value assumptions, comments, value
records) carries
`account_id NOT NULL`. The shared reference catalog (`use_cases`, `data_assets`,
domains, sources, edges) has none. `server/accounts.py` resolves the active unit for
each request into a context variable, and membership (`account_members`) gates
access. Readiness reads data status per unit through the `asset_status_by_account`
view, so one unit never sees another's landed data.

## Storage

`server/db.py` is the only way code reaches app state: `fetch / fetchrow / fetchval /
execute / executemany / transaction / run_script`, written once in **Postgres SQL**
with `$n` parameters. `STORAGE_BACKEND` selects the implementation:

- **`lakebase`** (`server/storage/lakebase.py`): asyncpg pool, the app's OAuth token
  as the password, refreshed about every 45 minutes. SQL runs as written.
- **`delta`** (`server/storage/delta.py`): Databricks SQL connector to the bound
  warehouse. `server/storage/translate.py` turns each statement into a Databricks SQL
  plan with sqlglot. It caches by SQL text and binds parameters as escaped literals in
  the parsed tree. What a dialect swap can't cover is driven by
  `server/storage/schema_meta.json` (keys, auto-id columns, foreign keys):
  - `INSERT … ON CONFLICT` → `MERGE`, including `EXCLUDED.*` and conditional updates.
  - `RETURNING` → reads of the affected keys before or after the write.
  - Auto-increment ids → time-based 64-bit ids generated by the app.
  - `ON DELETE CASCADE / SET NULL` → child deletes or updates issued first.
  - `= ANY(array)` → `array_contains`. `jsonb_agg` / `jsonb_build_object` →
    `to_json` / `named_struct`. Aggregate `ORDER BY` → sorted keyed structs.
  - Correlated scalar subqueries → `any_value` / `max_by`. A primary-key
    `GROUP BY` → all of that table's columns.

  Reads are cached in-process and invalidated by writes to the tables they read.
  Conflicting concurrent writes are retried.
  `tests/integration/check_delta_sql.py` `EXPLAIN`s every static statement against a
  real warehouse, and `tests/integration/smoke.py` exercises the running app on
  either backend.

### Schema and migrations

Postgres is the schema of record:

- `server/migrations/001_baseline.sql`: the 1.x schema. Its `account_assessments` and
  `account_promotions` tables are no longer written (the assessment moved out of the
  app in 2.0) and are kept so an upgraded install loses nothing.
- `server/migrations/002_roadmap_import.sql`: roadmap import (`roadmap_imports`,
  `account_pillars`, `account_roadmap_use_cases`). Additive.
- `server/migrations_delta/NNN_*.sql`: the Delta equivalent of each, **generated** by
  `scripts/gen_delta_schema.py` from a database with the Postgres migrations
  applied, together with `server/storage/schema_meta.json`. The generator only writes
  files that do not exist yet, since an applied file is checksummed.

Later changes are new numbered files in **both** directories, with the metadata
regenerated. `tests/test_storage_schema.py` fails if the three drift apart.
`server/migrator.py` applies pending files once each, in order, recorded with a
checksum in `schema_migrations` (transactionally on Lakebase; statement by statement,
recorded last, on Delta). It refuses to continue on drift. Migrations are applied only
by the bundle's setup job (`scripts/setup.py`, running as the deployer). The app's
service principal holds DML only, and app startup only reports schema state.

### Reference catalog

`reference/catalog.json` is the shipped catalog: use cases with value models, data
assets, domains, data sources and rollups, requirement and dependency edges, default
value assumptions, and the worksheet-id crosswalk. `server/reference.py` seeds it on
setup: missing rows only by default, or all catalog rows with `--refresh-catalog`.
Reference rows keep their small ids; ids created in the app start at 1,000,000.
`scripts/export_reference.py` is the maintainer tool that produced the bundle from a
curated instance, reading reference tables only. `scripts/check_names.py` fails CI if
any shipped file names a real company, person, or internal host.

## Readiness, phase, value

- `server/readiness.py`: the single definition of "is this use case's data ready",
  with a dual path (data domains when declared, else module requirements) plus
  prerequisites. It reads the requirement structure once (`_readiness_inputs`, static
  SQL) and evaluates readiness in Python for the business unit's ready set, so the
  what-if simulator (`status_override`) runs the same logic many times cheaply.
- `server/phase.py`: phase is derived from the depth of the enables graph, never set
  by hand.
- `server/value_engine.py`: evaluates parameterized value models against the business
  unit's value assumptions.

## Agents

All model calls go through `server/llm.py` and the shared helpers in
`server/routes/agents.py`. Those helpers negotiate optional parameters per endpoint
and accept structured output, with a schema-free retry. Every agent that proposes a
write returns a preview. The write happens only when a person confirms the single-use
token (`server/confirm.py`, `POST /api/confirm/{token}`). Agents validate model output
against the catalog and drop anything they can't resolve. They fall back to
deterministic results when the endpoint is unavailable.

## Deployment

`databricks.yml` defines the app (command, environment, resources), the setup job,
and a job run triggered on every `bundle deploy`, with two targets:

- `lakebase` adds a Lakebase project and binds its default database to the app
  (`CAN_CONNECT_AND_CREATE`).
- `delta` sets the app-state catalog and schema.

`scripts/setup.py` is idempotent: storage, migrations, catalog, first business unit
and admins, grants. The same script runs from a laptop with `--profile`.
`server/backup.py` with `scripts/restore.py` provides backend-neutral backup and
restore.
